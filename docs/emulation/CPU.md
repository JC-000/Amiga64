# The 68000 interpreter

The guest CPU is a Motorola 68000 interpreted by 6502 code. The core is
`runtime/core.s`; the instruction families are `runtime/ops/g1_move.s`
through `g6_muldiv.s`. The binding interface is
[CONTRACTS.md](../CONTRACTS.md) "Zero-page register file", "Interpreter
ABI", "Code-window cache", "Dispatch" and "Supervisor mode & exceptions".

## What is implemented

- The 68000 **user-mode integer** instruction set (all of it except TAS
  and MOVEP, below), with a 24-bit,
  big-endian address space (CONTRACTS "Guest model").
- **Supervisor mode and exception processing** behind one flag, `st_exc`
  (Wave 6). Machine mode (AROS) runs with it on; program mode runs with it
  off.
- **Interrupts** (autovectors 25-30) delivered by the machine loop, not by
  the core ([CIA_AND_TIMING.md](CIA_AND_TIMING.md)).
- Two instructions are legal but not implemented and always halt
  `HALT_ILLEGAL`: **TAS** and **MOVEP** (CONTRACTS "Flag set" table).

## The register file

All 68000 registers live in the C64's zero page, little-endian (the memory
API converts to the guest's big-endian at the REU boundary). The
authoritative map is `runtime/rc/zp.inc`.

| ZP | Contents |
|---|---|
| `$10-$2F` | D0-D7, 4 bytes each (`r_d0` = `$10`) |
| `$30-$4F` | A0-A7; A7 is the **active** stack pointer |
| `$50-$53` | PC (`r_pc`) |
| `$54` | CCR in native bit order: X = bit 4, N = 3, Z = 2, V = 1, C = 0 |
| `$55` | the SR system byte: T (stored, tracing not modelled), S, I2-I0 |
| `$56-$57` | the current opcode word (`op_lo`/`op_hi`) |
| `$58-$5F` | memory API arguments `m_addr`, `m_val` |
| `$60-$77` | EA and ALU operands and scratch (`t_ea`, `t_op1`, `t_op2`, `t_res`, `t_tmp`) |
| `$78-$79` | `st_halt`, `st_reason` |
| `$7A-$7F` | core-internal: `ea_kind`, `ea_reg`, `ea_size`, `st_step`, `w_zacc`, `w_ptmp` |
| `$80-$87` | fetch-window and REC-shadow state |
| `$88-$94` | exception state: `st_exc`, the inactive SP `r_osp`, the instruction snapshot `st_ipc`/`st_iop`/`st_sp6`, the latched flag `st_exl` |
| `$95-$99` | machine loop: `ev_pend`, `mach_frames` |

Register *n* is at ZP `$10 + 4n` (D0-D7 = 0-7, A0-A7 = 8-15), which the
`getreg`/`setreg` macros use. `$02-$0F` belong to the loader and harness
and are never touched by the interpreter.

## The step loop and dispatch

`emu_step` executes exactly one instruction; `emu_run` loops until
`st_halt` is nonzero. Each step fetches the opcode word, then jumps through
a 256-entry table indexed by the opcode's high byte. The table is
generated by `host/gen_dispatch.py` into `build/gen/dispatch.s` and lives
page-aligned at `$0900-$0AFF`; nobody edits it by hand.

| `op_hi` | Family |
|---|---|
| `$00-$0F` | immediate ops, bit ops, MOVEP (halts) |
| `$10-$3F` | MOVE, MOVEA |
| `$40-$4F` | miscellaneous: CLR/NEG/NOT/TST, EXT/SWAP, LEA/PEA, JSR/JMP/RTS/RTR/NOP, MOVEM, CHK, system ops |
| `$50-$5F` | ADDQ/SUBQ, Scc, DBcc |
| `$60-$6F` | BRA/BSR/Bcc |
| `$70-$7F` | MOVEQ |
| `$80-$8F` | OR, DIVU/DIVS, SBCD |
| `$90-$9F` | SUB, SUBA, SUBX |
| `$A0-$AF` | A-line: `$AFFF` = HALT, `$A1xx` = an HLE call, else a trap |
| `$B0-$BF` | CMP, CMPA, CMPM, EOR |
| `$C0-$CF` | AND, MULU/MULS, ABCD, EXG |
| `$D0-$DF` | ADD, ADDA, ADDX |
| `$E0-$EF` | shifts and rotates |
| `$F0-$FF` | F-line |

Each family decodes the rest of the opcode itself. All condition-code
logic is in a small set of sized ALU primitives in `core.s` (`alu_add`,
`alu_sub`, `alu_cmp`, …), not in the families. Effective addresses for
every 68000 mode are resolved by `ea_calc`/`ea_load`/`ea_store`. An
unimplemented secondary decode jumps to `op_illegal`; nothing is silently
skipped (CONTRACTS "Dispatch").

### Halts

`st_reason` says why a run stopped (`runtime/macros.inc`, `core.s`):

| Code | Name | Meaning |
|---|---|---|
| `$00` | `HALT_OK` | the pseudo-op `$AFFF` (clean program end) |
| `$01` | `HALT_ALINE` | an A-line word with exceptions off (an unimplemented HLE slot holds `$A0FF`) |
| `$02` | `HALT_FLINE` | an F-line word with exceptions off |
| `$03` | `HALT_ILLEGAL` | an illegal or unimplemented encoding (with exceptions off, also every privileged op) |
| `$04` | `HALT_STOP` | STOP in exception mode; `mach_run` handles it and passes it up only when nothing can wake the CPU |
| `$05` | `HALT_ADDRESS` | an odd PC from a vector or RTE (address errors are only this code) |
| `$57` | `TD_HALT_MOD` | a resumed snapshot's td module does not match ([STORAGE.md](STORAGE.md)) |

## Instruction fetch: the code-window cache

Instruction words are not read from the REU one at a time. `fetch_word`
serves them from a 256-byte, page-aligned copy of the guest code page in
C64 RAM. Since Wave 12 there are **7 such windows** (`CWIN_N`), at `$A900`,
`$AA00`, … `$AF00`, in RAM under the BASIC ROM, with a page-low summary map
at `$B000` (CONTRACTS "Code-window cache").

- **Hit:** the PC's page is the current window's page: two loads, no DMA.
- **Miss:** another cached window may hold the page (no DMA); otherwise
  the window at the FIFO hand is refilled with **one 256-byte REU DMA**.
  FIFO was chosen over LRU: on the AROS boot it leaves 1.0% more refills
  at N = 7 and costs nothing on a switch (`build/evidence/w12-cwin/policy.txt` in the main checkout,
  quoted in CONTRACTS).
- **Self-modifying code:** every `mem_write*` checks the map, and a write
  into a cached page drops that window. Code that writes guest memory
  without the memory API must invalidate explicitly: the blitter calls
  `code_invpg` per destination row, the trackdisk per chunk, and a
  snapshot resume calls `code_invall`.
- **Page ends:** a fetch is always one word at an even PC, so no window
  needs a 257th byte; the next page's words come from that page's window.

The window hit path costs the same as the single-window core it replaced.
The write check costs 13 cycles on the common path (it was 9 for bytes and
16 for words/longs) (PERF (n)).

## Data memory

Data reads and writes go through the memory API (`mem_read8/16/32`,
`mem_write8/16/32`), one REU DMA per call, with a **REC shadow** that skips
REU-controller register writes whose values have not changed. Accesses to
banks `$BF` and `$DF` never reach the REU: they are the CIAs and the custom
chips. See [MEMORY.md](MEMORY.md).

## Supervisor mode and exceptions

With `st_exc` set (CONTRACTS "Supervisor mode & exceptions"):

- `r_sr+1` is the real SR system byte (writes masked to `$A71F`), A7 is the
  active stack pointer and `r_osp` the inactive one; every S change swaps
  them.
- Privileged ops (ANDI/ORI/EORI to SR, MOVE to SR, MOVE USP, RTE, STOP,
  RESET) work in supervisor mode and raise a privilege violation in user
  mode.
- TRAP, TRAPV, CHK, divide by zero, illegal, A-line and F-line take their
  vectors with a 68000 group 1/2 frame (SR word, then PC long); the vector
  base is fixed at 0.
- **STOP** halts the CPU until an interrupt; the machine loop waits for one
  (or returns `HALT_STOP` if nothing could ever wake it).
- `emu_reset` *latches* the flag, so changing `st_exc` takes effect only at
  the next reset.

Not modelled: address and bus errors (only `HALT_ADDRESS`, for an odd
vector or RTE target), an odd supervisor stack while a frame is built,
tracing (T is stored but never acted on). Known gap: some encodings that
are illegal on a 68000 because of their addressing mode (for example
`LEA (A0)+,A1`) execute instead of raising vector 4 (the full list is in
CONTRACTS "Known gap").

With `st_exc` clear (program mode, and the golden vector suite), every
trap-like event halts with its reason code instead, bit for bit as before
Wave 6.

## How fast it is

Measured on real hardware (docs/HARDWARE.md):

| Workload | U64E "48 MHz" | Source |
|---|---|---|
| ALU loop (ADDQ.L/ADD.L/DBRA) | 75-80k instructions/s | HARDWARE "REC shadow core", "Windowed core" |
| memory loop `MOVE.L (A0),D1` | 68-72k/s | "REC shadow core" (compare only within a session) |
| read-modify-write `ADDQ.L #1,(A0)` | about 58k/s | "REC shadow core" |
| AROS boot to m1 (ROM checksum, RomTag scan) | about 62k/s | PERF (l) |
| AROS between m1 and m2, at `s` = 2..5 | about 29-37k/s [derived from PERF (l): model instructions m1→m2 over the wall time between them]; PERF's prose: 25-39k after m1 | PERF (l) |
| an idle guest loop in the player profile (`s` = 0) | 84.1k/s | HARDWARE "Paula on the U64 sampler" |

On light code that is about a 0.8-1 MHz 68000 (HARDWARE finding 7);
the AROS boot runs at about 75-80% of that rate to m1, and at roughly a
third to a half of it between m1 and m2. The A500
runs at 7.09 MHz. The practical ceilings found on the U64E: an
REU-controller register access costs about 1.7-1.9 µs at 8-24 MHz and
0.9-1.0 µs at 32-48 MHz, so it stops scaling with the CPU clock, and bulk
REU DMA stops scaling above
about 2 MHz at about 3.3 MB/s (HARDWARE "Findings"). Those, not the 6502's
clock, set the interpreter's limits; the fetch window and the REC shadow
exist because of them.

The C64U at 64 MHz was not benchmarked the same way. Its measured
end-to-end times (Workbench boot 130.5 s against 147-155 s on the U64E)
are in docs/HARDWARE.md "Workbench 3.1 from the ADF".

VICE runs the same code but says nothing about speed: warp mode only
removes real-time pacing from a 1 MHz machine (CONTRACTS "Verification
commands").

## How it is tested

- **Golden vectors:** sampled [SingleStepTests 680x0](https://github.com/SingleStepTests/680x0)
  cases (Musashi-generated) run one instruction each, and every register,
  flag and memory byte is compared. The current golden set is 5129 cases
  (5150 sampled, minus 21 that touch the I/O banks), all green in VICE and
  on a U64E (CONTRACTS "Vector sets", HARDWARE "Suite results").
- **Hand vectors:** 63 (48 for ops the upstream suite lacks, 15 for
  512 KB REU-line straddles and bank carries).
- **Supervisor vectors:** `python3 -m host.vectors --set super` plus the
  hand set `SUPERHAND`, run by `tests/run_super_vectors.py`.
- **Self-modifying code and the cache:** `tests/smc.py`, `tests/run_cwin.py`.
- **Cycle budget:** `tests/perf_cycles.py --max-delta 0` fails if a change
  adds cycles to the per-instruction paths.

See [TESTING.md](TESTING.md) for how to run them.

## Where to change things

- A new instruction or a decode fix goes in the owning family file; the
  family map is in CONTRACTS "Dispatch". Rebuild with `make runtime`, then
  run `make vice-test`.
- Hot-path branches are wrapped in the `BRNC` macro, which fails the link
  if a taken branch would cross a page (an extra cycle per instruction).
  RODATA is page-aligned so that table reads keep their page offsets
  (`runtime/c64.cfg` comments).
- The main PRG area is full (Waves 15-17 briefs: "MAIN is full"); new code
  for machine mode goes into a module, not into the PRG.
